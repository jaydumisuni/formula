# Cross-Domain Certificate Atlas Research Pass

Date: 2026-08-28
Status: research checkpoint
Repository name: temporary only; not product identity

## Purpose

The project depends heavily on the architecture:

```
large/complex/untrusted producer
        ↓
compact witness/certificate
        ↓
small independent checker
```

This pass asks how broadly that pattern actually applies.

The answer is: **very broadly, but not universally and not always with the same asymptotic advantage.**

The certificate family must therefore be part of the Theory Profile.

## General evidence: certifying algorithms

The certifying-algorithms literature defines algorithms that return an output plus an easy-to-check correctness witness. Surveys report 100+ examples, including connectedness, strong connectedness, shortest paths, minimum spanning trees, maximum flows, maximum matching, graph recognition, number theory, and optimization.

Sources:
- https://people.mpi-inf.mpg.de/~mehlhorn/ftp/master-final.pdf
- https://www.mpi-inf.mpg.de/news/spotlight-articles/how-to-trust-the-output-of-your-program

The important engineering lesson is instance correctness:

```
correct algorithm proof
    !=
correct implementation instance

certificate + checker
    -> checks this actual output
```

## Atlas

### Integer primality

Result:
```
N is prime
```

Witness families:
- Pocklington / N-1 certificates;
- ECPP certificates;
- APRCL-style proving routes.

PARI exposes `primecert` and `primecertisvalid`; its ECPP certificate recursively reduces primality to smaller certified primes and elliptic-curve conditions.

Sources:
- https://pari.math.u-bordeaux.fr/dochtml/html/Basic_number_theory.html
- https://pari.math.u-bordeaux.fr/dochtml/ref/Arithmetic_functions.html

Checker cost can be dramatically lower and simpler than discovering the proof.

### Integer factorization

Claim:
```
N = p1^e1 ... pk^ek
with all pi prime
```

Witness:
```
factor list
+ multiplication equality
+ primality certificate for every factor
```

The hard factor search can be completely untrusted once those checks pass.

### GCD / Bézout

Claim:
```
g = gcd(a,b)
```

Witness:
```
x,y such that g = xa + yb
and g divides a,b
```

This is a classic certifying-algorithm example.

Source:
- https://people.mpi-inf.mpg.de/~mehlhorn/ftp/master-final.pdf

### SAT

SAT result:
```
SAT
```

Witness:
```
truth assignment
```

Checker evaluates all clauses.

UNSAT result:
```
UNSAT
```

Witness families:
- DRAT/LRAT-style proof traces;
- verified LRAT checkers.

This is already covered in the certificate baseline and CakeML checker research.

### SMT

SAT witness:
- model/assignment, theory-dependent checking.

UNSAT witness:
- Alethe proof or solver-native proof translated to a checkable form.

cvc5 + Carcara provides a concrete producer/checker separation for supported theories.

### Term rewriting

Claims:
- termination;
- confluence;
- complexity;
- completion properties.

Certificate:
- CPF (Certification Problem Format).

Checker:
- CeTA, generated from Isabelle/HOL formalizations.

This is a major example of one certificate family covering multiple theory properties.

### Equality saturation

Claims:
- two terms are in the same equality class;
- extracted term is equivalent;
- extracted term has minimum additive cost within the certified e-class/extraction model.

Witness:
- merge/extraction certificate.

Checker:
- Isabelle AFP verified checker for egg certificates.

### Exact polynomial/algebraic relations

Claims:
- polynomial identity;
- ideal membership;
- Gröbner basis consequence;
- infeasibility.

Witnesses:
- explicit reduction/remainder to zero;
- change-of-basis/representation matrices;
- Nullstellensatz certificate (`1` generated by the constraint ideal);
- Positivstellensatz/SOS certificate for ordered-real infeasibility/nonnegativity.

These can turn enormous symbolic searches into finite algebraic identities checked by arithmetic.

### Polynomial-system roots

Claims:
- approximate point corresponds to an exact root;
- unique root in box;
- no root in box.

Witness/checker routes:
- Smale α-theory (`alphaCertified`);
- Krawczyk operator;
- interval Newton inclusion/exclusion.

Sources:
- https://arxiv.org/abs/1011.1091
- https://arxiv.org/abs/2011.05000

### Linear algebra: matrix product

Claim:
```
AB = C
```

Deterministic checker:
- exact recomputation.

Probabilistic checker:
- Freivalds-style randomized vector checks, with explicit error probability.

The certificate class must distinguish deterministic from probabilistic verification.

### Linear algebra: rank / rank profile / determinant

Witness families:
- nonzero minors / independent vectors for lower-rank bounds;
- factorizations for upper-rank bounds;
- elimination/factorization certificates;
- interactive rank-profile/determinant protocols.

Research provides certificates whose verification can be cheaper than recomputation, including constant-round protocols based on matrix-vector products.

Sources:
- https://arxiv.org/abs/1702.03755
- https://arxiv.org/abs/1909.05692

### Linear systems

Claim:
```
Ax = b
```

Witness:
```
x
```

Checker:
```
compute Ax and compare to b
```

For uniqueness/invertibility:
- inverse/factorization/determinant/rank certificate.

For infeasibility:
- dual/Farkas-style witness where applicable.

### Shortest paths

Claim:
```
D(v) = distance(s,v)
```

A classic certificate combines:
- path/predecessor witnesses achieving `D(v)`;
- edge inequalities `D(v) <= D(u)+c(u,v)` proving no shorter edge relaxation exists.

Source:
- https://people.mpi-inf.mpg.de/~mehlhorn/ftp/master-final.pdf

For negative-cycle detection, the cycle itself is a direct witness.

### Minimum spanning tree

Claim:
```
T is an MST
```

Certificate families use spanning-tree validity plus cut/cycle optimality information. Certifying MST algorithms are part of the established LEDA/certifying-algorithm corpus.

Source:
- https://people.mpi-inf.mpg.de/~mehlhorn/ftp/master-final.pdf

### Maximum flow

Primal witness:
```
feasible flow f
```

Dual witness:
```
s-t cut C
```

If:
```
value(f) = capacity(C)
```

then max-flow/min-cut duality proves optimality.

Source:
- https://cp-algorithms.com/graph/edmonds_karp.html

This is an ideal example of a compact primal/dual optimality certificate.

YES witness:

```

NO witness:

```

### Connectivity / strong connectivity

YES witnesses:
- spanning tree / reachability trees;
- forward/backward reachability structures for strong connectivity.

NO witnesses:
- separated components / unreachable pair with suitable cut/reachability evidence.

Verified checkers exist in the certifying-graph-algorithm literature.

### Maximum matching

Primal witness:
```
matching M
```

Optimality witness:
- Tutte/Berge/barrier/blossom-related dual structural evidence depending on graph class/algorithm.

Certifying maximum-matching algorithms and formally verified checker work exist in the LEDA/Isabelle line.

Source:
- https://www.mpi-inf.mpg.de/people/mehlhorn/

### Planarity / graph recognition

YES witness:
- combinatorial embedding/rotation system with checker.

NO witness:
- forbidden/minor/subdivision-style obstruction (e.g. Kuratowski-type structure) where applicable.

Certifying graph-recognition algorithms explicitly use positive and negative witnesses.

### LP / MILP

Claims:
- feasible solution;
- optimal solution;
- infeasibility;
- unboundedness.

Witnesses:
- primal solution;
- dual solution/bounds;
- Farkas certificate;
- branch-and-cut/VIPR proof log.

SCIP exact mode + VIPR/CakeML checker gives a concrete industrial path.

Sources:
- https://www.scipopt.org/doc-10.0.0/html/EXACT.php
- https://github.com/scipopt/vipr

### Convex optimization

Witnesses:
- primal/dual feasible points;
- zero/small certified duality gap;
- KKT conditions when assumptions/constraint qualifications are established;
- conic dual certificates.

The certificate scope must include strong-duality assumptions.

### Polynomial global optimization

Witnesses:
- SOS/Positivstellensatz positivity certificates;
- moment/dual bounds;
- convergent Lasserre-hierarchy bounds.

A closed lower/upper bound proves global optimum.

### Rigorous numerical evaluation

Claim:
```
true value lies in interval/ball B
```

Witness:
- directed-rounding/interval computation proof path or independently checkable enclosure calculation.

For predicates:
- interval excluding zero/boundary certifies sign/order/member result.

### Correct rounding

Claim:
```
float y = correctly rounded f(x)
```

Witness principle:
- compute rigorous enclosure `[l,u]` for exact `f(x)`;
- prove both endpoints round to the same target float.

Ziv-style refinement repeats until decisive.

### Differential/recurrence solutions

Candidate solution `f` can often be checked by:
- substitution into defining equation/recurrence;
- initial/boundary conditions;
- separate uniqueness theorem/certificate.

The candidate finder may be arbitrary; verification is structural.

### Quantifier elimination over reals

Claim:
```
quantified formula φ ≡ quantifier-free ψ
```

Certificate/authority routes:
- formal real-closed-field QE;
- CAD/projection result with independently certified equivalence where available.

Formal Rocq developments establish certified QE algorithms for discrete real closed fields.

### Automated theorem proving

Claim:
```
Γ ⊢ theorem T
```

Witness:
- proof term / proof object / foundational certificate.

Checker:
- small kernel or certificate checker.

This remains the strongest generic authority route when a domain-native compact certificate is unavailable.

## Important gaps / hard cases

The atlas must preserve where compact certification is not generally available.

### Exact counting (#P-style)

A proposed count of satisfying assignments or combinatorial objects does not in general have an obvious tiny deterministic certificate comparable to one SAT assignment.

Possible routes include:
- compiled decision diagrams/knowledge representations that can be rechecked;
- algebraic proof systems;
- interactive/probabilistic proofs;
- exact recomputation in a reduced representation.

The project must not pretend every exact count has a cheap certificate.

### General arithmetic-circuit identity

A counterexample to equality can be tiny: one evaluation point where outputs differ.

But proving equality of arbitrary succinct arithmetic circuits is Polynomial Identity Testing; efficient deterministic PIT for general circuits remains open. Randomized tests exist but carry probability semantics.

So:
```
NON-EQUIVALENT may have easy witness
EQUIVALENT may be much harder
```

### Arbitrary program semantic properties

Rice/halting barriers remain. No universal certificate route turns every arbitrary semantic program property into a decidable problem.

### Global minimality / shortest representation

Kolmogorov-complexity limits prevent universal certificates of absolute globally shortest representation. Minimality must be relative to a finite/decidable representation class/cost model.

## Architecture consequence: certificate polarity

A problem may have different witness complexity for positive and negative answers.

The Theory Profile should therefore describe certificates by **result polarity**, not only by problem class.

Example:

```
SAT:
  YES -> assignment (tiny)
  NO  -> proof trace (potentially large)

primality:
  PRIME -> ECPP/Pocklington certificate
  COMPOSITE -> nontrivial factor is immediate witness

bipartite:
  YES -> coloring
  NO  -> odd cycle
```

This affects search scheduling dramatically.

## Proposed certificate-atlas schema

Each capability/problem family should eventually record:

```
result_class
witness_family
checker_family
checker_trust_root
producer_need_not_be_trusted: true/false
verification_complexity
certificate_size_bound
probabilistic_or_deterministic
positive/negative polarity
completeness
foundation/assumption requirements
reconstruction requirements
```

## Core conclusion

> **The solver/verifier split is not a niche architecture. It is a pervasive mathematical pattern across number theory, graphs, algebra, logic, optimization, and validated numerics.**

But certificate availability and compactness are domain- and polarity-specific.

The project therefore needs a **certificate router/atlas**, not one universal proof format and not the assumption that every result is cheaply certifiable.

## Next research

1. Fill the atlas with exact complexity/size bounds for each certificate family.
2. Identify domains where interactive certificates are substantially smaller than static ones.
3. Determine which interactive/probabilistic protocols can be made noninteractive/replayable in the project context.
4. Map certificate composition through reductions, morphisms, black boxes, and compiled realizations.
5. Identify major capability gaps where exact results lack practical certificate routes; these become targeted research obligations.
